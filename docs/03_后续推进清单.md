# 后续推进清单｜以人工验收为主

## A. 第一优先级：评审3个Consider

### 1. 可审计的财报异常识别与证据引用

需要人工确认：

- 是否有明确使用者、频率和错误成本。
- 补充真实分析师访谈原文或SOP，而非内部摘要。
- 完成FinanceBench、FinQA、TAT-QA、FinanceBenchmark.ai等Coverage Matrix。
- 将Gap限定为可验证的任务组合，不使用“现有评测均未覆盖”的泛化表述。

通过条件：真实Workflow Verified；至少3个直接相关Benchmark完成协议级覆盖分析；目标任务仍存在明确残余Gap。

### 2. Agent执行轨迹的人工审查、理解与复用

需要人工确认：

- 是否接受“人机系统Benchmark”而非纯模型Benchmark。
- 定义用户理解、错误发现、修改成功率和复用效率指标。
- 判断N=20的Trace2Flow研究是否足以支撑Pilot。
- 补查Trajectory/HCI评测，确认没有直接同类公开Benchmark。

通过条件：评价对象和决策场景清晰；真人实验成本可接受；Coverage Analysis支持残余Gap。

### 3. AI共创中的用户信息吸收度

需要人工确认：

- “吸收”是识别、理解、延迟记忆还是迁移应用。
- Benchmark目标是评模型、产品交互设计，还是人机系统。
- 是否能获得真实参与者并完成伦理与实验设计。
- 检查TraceMind数据是否公开、是否允许复用。

通过条件：构念定义稳定；指标可复现；真实任务方认可其决策价值。

## C2. Coverage Probe：外部目录检索

`radar/evidence/coverage_probe.py` 用 benchmark-radar 开源目录（1,284 条 Benchmark 记录，来自
llm_stats / artificial_analysis / model_reports / opencompass_hub）为每个 Idea
检索可核查的 Coverage 候选，替代人工维护的静态 Existing Benchmark 名单。

```bash
# 首次：装好 benchmark-radar 的 venv（之后不用再装）
cd /Users/prince/benchmark-radar
uv venv --python 3.12 .venv && uv pip install --python .venv/bin/python -e .

# 检索并写入 benchmark_coverage（先 --dry-run 复核筛选口径）
cd /Users/prince/Benchmark-Idea-Radar
python3 -m radar.evidence.coverage_probe --dry-run --idea 1 --limit 10
python3 -m radar.evidence.coverage_probe --limit 10
python3 -m radar.evidence.coverage_probe_report
```

脚本每次运行前自动执行 `benchmark-radar sync`，从 `benchmark-radar.org` 拉取
最新目录数据，并把数据版本记进报告的 `catalog_sync` 字段——核查结论只对该
版本的目录成立。`--no-sync` 可跳过同步用本地已有版本。

产出：`outputs/coverage_probe/coverage_review.md` / `.json`。

口径约束：

- 目录是**聚合 secondary 源**，不是 Raw Source；记录只含 name/description/
  categories，不含 task definition、input/output 与 evaluation protocol。
- 因此写入的 coverage 行一律 `target_coverage=unknown` +
  `verification_status=needs_review`，**不能据此判定 covered 或 not_covered**。
  要定论必须人工核查原始 Paper/Repo。
- 已有人工核查行（`verified` / `partial`）受保护，不会被检索结果覆盖。
- 全部候选连同 `rejection_reason` 写入 `retrieval_runs` / `retrieval_results`，
  被拒记录同样可追溯。
- 检索不使用 `ideas.evaluation_gap`：库中多条该字段被 arXiv 摘要原文污染
  （idea 18/9/4/6/11），作为检索输入会引入噪声。查询由 `IDEA_TOPIC_TERMS`
  人工主题词 + domain + capability 构造。

首轮结论（2026-09-23，23 个 Idea / 46 条查询 / 203 条候选入库）：

| Verdict | Idea 数 | 含义 |
|---|---:|---|
| `topic_too_wide` | 15 | 命中 ≥8 条同领域基准，当前检索输入下无区分度 |
| `needs_manual_coverage_analysis` | 8 | 少量候选，需人工核查原文定论 |

**`topic_too_wide` 这 15 个不能直接当"主题过宽"的证据。** 它们恰好全是
`IDEA_TOPIC_TERMS` 里没有主题词、回退到 capability 宽词检索的 Idea——用
"domain reasoning""planning"这类词去查必然命中一堆，无法区分"Idea 真的宽"
和"检索输入太泛"。要定论需先给它们补人工主题词再跑一次。

更根本的原因见 `radar_core.py:39` 的 `THEMES` 表：只有 8 行关键词规则，命中
就归入对应主题，命不中就兜底命名 `"{domain} {capability}能力评测"`。那 15 个
正是兜底产物——它们不是过宽的主题，而是未被规则覆盖的剩余物。Coverage Probe
对表内的 8 个主题有意义，对兜底项意义有限。

3 个 Consider 的待核查对象：

- **Idea 1 财报异常识别**：FinQA、Big Finance Bench。注意目录里 FREB-TQA、
  TableEval 等表格 QA 基准未带 finance 类目，靠跨领域降级通道进入，仍需核查
  其数据来源是否为财报。
- **Idea 2 合同跨条款审查**：目录内**没有**任何条款级审查基准，仅命中
  Uniform Bar Exam（律考，非条款审查任务）。此前据 CLAUSE 2026 判定"已被覆盖"
  的结论在本目录中查不到支撑——CLAUSE 2026 不在目录内，需单独核实该判断来源。
- **Idea 18 临床推理与指南溯源**：新增 CRPErelation、MedXpertQA、MedAgents-Bench、
  MedBrowseComp、ER-Reason、MedBookVQA 六条，需与既有 CMB / MedQA /
  LLMEval-Med / CliMedBench 人工核查合并判断。

命中数反差：兜底命名的 Idea 命中 10–17 条，`THEMES` 表内的精确主题 Idea 只
命中 1–6 条。这个反差反映的是检索输入的宽窄，先补主题词再复跑才能判断 Idea
本身是否过宽。

## D. 每周人工评审动作

1. 查看本周新增Signal，不直接接受自动聚类命名。
2. 检查Idea最初触发源是否为Raw Source。
3. 优先补Existing Benchmark Coverage，而不是先补Model Failure。
4. 对每个负向Gap写明“核查了哪些Benchmark”。
5. 给出Recommend / Consider / Watch / Reject。
6. 只有Recommend才进入正式立项；Consider继续补证据，不自动进入Mini Eval。

## E. 立项Gate

正式立项前至少满足：

- 真实Workflow：Verified。
- Existing Benchmark Coverage：至少3个直接竞品完成协议级核查。
- Evaluation Gap：由Coverage Matrix支持，不是LLM推断。
- 可评判性：任务输出与评分规则明确。
- 数据来源与合规可行。
- Model Failure可以是Unsupported；如果将其作为立项理由，则必须有公开可靠结果或Case级证据。
